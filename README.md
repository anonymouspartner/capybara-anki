# capybara-anki

A self-owned spaced-repetition app for one couple learning each other's languages —
offline reviewer, page scanner, and pronunciation practice, backed by the same
Postgres the Capybara Telegram bot already writes to.

**Steps 0 and 1 are built** (migration, verified against a real export; schema and
FSRS replay). Nothing user-facing exists yet — no reviewer, no deploy. Read
[`docs/DESIGN.md`](docs/DESIGN.md) first; it is the plan of record and explains why
this exists at all.

---

## Why this is not just "use Anki"

Anki is free and open source, and replacing it for cost reasons would be silly. The
reason is that the current pipeline is one-way:

```
bot  ─┐
      ├─► CSV / .apkg ─► AnkiDroid ─► (nothing)
scan ─┘
```

Every signal about what is hard, what lapsed and what stuck lives on a phone, inside
an app that does not talk back. Nothing upstream can act on it. This closes that loop.

A secondary benefit: roughly a third of the scanner's complexity exists only to hand
files to a foreign app, and goes away when the scanner writes rows instead.

## Ground rules

Inherited from `capybara-bot`, and they apply here too:

- **No deploys without an explicit, in-the-moment request.** The maintainer runs every
  deploy.
- **No Supabase changes** — migrations, SQL, dashboard — without the same explicit
  request. This app shares a project with the live bot.
- **No secrets in code or git.** Everything via environment.
- **Never commit a collection export, or anything derived from the corpus.** Exports
  carry vocabulary drawn from private conversations. `.gitignore` blocks the obvious
  extensions and all of `scratch/`, but the rule is the rule, not the file. Test
  fixtures are synthetic collections generated by the suite.

## Migration CLI

`migration/` reads an Anki collection export and reports what's in it — read-only,
never touches Postgres, never deployed (see `docs/DESIGN.md` D7). See
[`migration/README.md`](migration/README.md) for how to get an export off a phone and
run it.

**Verified against a real AnkiDroid export, 2026-09-15**: 1094 vocabulary notes read
cleanly (204 pronunciation-practice notes correctly excluded), 4504 reviews spanning
three months, 1034/1094 cards carrying real FSRS memory state. Five real gaps between
the original design and the actual file were found and fixed along the way — see
`docs/DESIGN.md` §7.5 for what they were. 37 tests, all against synthetic fixtures
built with the real `anki` library (never the maintainer's actual collection),
CI-checked on every push.

## Schema and FSRS replay

`supabase/migrations/` has the real DDL for `notes`/`card_state`/`reviews`/
`scheduler_config` (docs/DESIGN.md §5) — **not applied anywhere**; see that file's
own header for why and for the open question of which repo's migration history
eventually carries it.

`src/fsrs/` implements §4.3's actual claim in TypeScript (Deno, `ts-fsrs`):
`card_state` is a fold over the append-only `reviews` log, and rebuilding it from
nothing must reach the exact same place as applying reviews one at a time. That's
not asserted, it's tested — `src/fsrs/replay.test.ts` builds a card's state both
ways and asserts they agree, alongside determinism and order-independence.

```bash
deno test --allow-read --allow-env src/
```

Building this surfaced one real fix to the schema itself: `card_state` needed a
`last_review` column that the original sketch didn't have. `ts-fsrs` derives elapsed
time from it, and — confirmed directly against the library — ignores whatever
`elapsed_days`/`scheduled_days` a resumed card carries. Real Anki independently
agrees: a card's own memory-state JSON carries the equivalent (`lrt`), found while
reading a real export during the migration spike.
